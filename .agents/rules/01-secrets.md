# Rowta rules: Secrets and security

Part of the binding Rowta rule set in `.agents/rules/`. Every rule has an ID; audits and reports cite the ID.
MUST and NEVER are absolute. [DECISION] = a choice made here that the owner can change. [VERIFY] = check against current official
documentation and cite the page. [OPEN] = waiting for the owner. Full legend: `00-core-process.md`.

---------------------------------------------------------------------------------------------------

## S. Secrets and security

S1. **NEVER write, print, log, echo or paste a real credential, key, token, password, code or webhook secret**
    into any output, file, log line, test fixture, screenshot or commit message. If a real sensitive value must
    appear for any reason, mask it first (asterisks, or a salted hash). The owner writes third-party `.env` values by hand;
    local secrets are generated by `scripts/setup-env.mjs`, which prints names only. You keep `.env.example` complete
    (names only, empty or obvious placeholder values; never an inline comment after an empty value, because some
    parsers read the comment as the value) and read names only.
S2. **NEVER open any `.env` or `.env.*` file except `.env.example`.** The scaffold already contains an `.env` with empty
    secrets. Programs you run (server, worker, tests, `docker compose up`) may load it; you never read, print, copy or edit
    it. Also forbidden because they print values: `printenv`, `env`, `set`, `Get-ChildItem Env:`, `docker compose config`,
    `docker inspect`, `docker compose exec ... env`, and echoing any variable that holds a secret. To check the file use only
    `node scripts/setup-env.mjs --check` (names and statuses, never values). Never ask the owner to paste `.env`.
S3. **Secret scan before every gate.** Run gates 3 and 3b in skill `rowta-gate-checks` (section 5): they search the repo (excluding
    `node_modules`, `.git`, `.agents`, lockfiles and every `.env*` file) for key prefixes, private-key headers, connection
    strings with embedded credentials and quoted secret-like assignments. Report file names and line numbers only. NEVER
    print the matching text. Also confirm `git ls-files` lists no `.env` file other than `.env.example`.
S4. **No secret in the app bundle.** No `EXPO_PUBLIC_` variable may hold a secret. Allowed: API base URL,
    Sentry DSN (public by design), EAS project ID. `docs/SECURITY.md` lists every `EXPO_PUBLIC_` variable and why
    it is safe.
S5. **The server decides everything that matters** (who the user is, their role, their team, what they paid,
    what they may see). The app only displays. A request from a tampered app MUST fail safely.
S6. **Permissions** are enforced by one central policy function on the server, deny by default, with a test for
    every cell of the PRD permission matrix (including the Staff "delete shift" call via a raw HTTP client).
S7. **Team isolation.** Every team-scoped query takes a required `teamId` through the data-access layer and
    filters by it inside the query. A query with no team scope MUST throw in tests. Cross-team resources return
    404, not 403, so existence is not leaked [DECISION]. Tests prove a user in team A cannot read, change or
    detect team B's data on every route. PostgreSQL row-level security is an optional second layer.
S8. **Never cache the user's role** on a token or in an index. Read it from `memberships` on each request so a
    demoted manager loses power at once.
S9. **Logs never contain** passwords, codes, tokens, secrets, full request bodies of auth routes, or full emails
    where a user ID will do. The logger has a redaction list and a test proves it.
S10. **Errors** never expose stack traces, SQL, file paths or library names. One error envelope (PRD 9.3).
S11. **HTTP hardening**: CORS allowlist (no wildcard with credentials), security headers, body size limits,
     request timeouts.
S12. **Dependencies**: lockfile committed; run the package audit command and report results; do not add an
     unmaintained package for auth, crypto or payments. Each new dependency needs a one-line justification.
S13. **Webhooks**: verify the signature over the RAW body before parsing, using a constant-time comparison; the
     scheme comes from the provider's current documentation [VERIFY], never from memory.
S14. **Rate limiting applies to EVERY route, not only the login form.** (a) A route cannot be registered without a
     named limit from the single config file (`server/src/security/limits.ts`, one row per limit with key, maximum,
     window, fail mode and a one-line reason); a test lists every route and fails when one has no limit. Skill
     `rowta-rate-limiting-recipes` holds the inventory and the values [DECISION]. (b) Counters are atomic and live in
     Redis, never in process memory; keys use `blake2b512` of the normalised email, token selector or IP, never the
     raw value. (c) The limiter runs BEFORE authentication, before Argon2id hashing and before any database work,
     so a flood cannot burn CPU. (d) Exceeded limits return 429 with `Retry-After` and the catalog message, and
     the body, status and timing are identical whether or not the account exists (A7). (e) Authentication,
     code, link, payment and invite routes FAIL CLOSED when Redis is unreachable (generic 503); read-only routes
     may fail open with a logged warning. (f) The client IP comes only from the trusted proxy setting
     `TRUST_PROXY_HOPS`; a spoofed `X-Forwarded-For` must not change the key. (g) Do not hard-lock an account after
     failures (an attacker could lock out the owner); slow the attacker with per-IP and per-target limits instead.
     (h) The payment provider's webhook is verified by signature (S13) with a cheap early reject and a generous
     limit; it is never blocked by the per-user limits. (i) The app shows the 429 message, disables the control
     until `Retry-After` passes, announces it, and never retries in a loop.
