# Rowta rules: User interface

Part of the binding Rowta rule set in `.agents/rules/`. Every rule has an ID; audits and reports cite the ID.
MUST and NEVER are absolute. [DECISION] = a choice made here that the owner can change. [VERIFY] = check against current official
documentation and cite the page. [OPEN] = waiting for the owner. Full legend: `00-core-process.md`.

---------------------------------------------------------------------------------------------------

## U. User interface

U1. **Authentication is a view, not a page.** One `AuthGate` screen renders one of these views from a small state
    machine: `signIn`, `signUp`, `verifyCode`, `forgot`, `resetCode`, `resetNewPassword`, `magicRequest`,
    `magicSent`, `magicConfirm`, `acceptInvite`. There are NO separate route files per auth view. Verified https links
    (`/invite/...`, `/magic#...`) open the app (`rowta://` forms are only a fallback) and set the view and its token in
    the machine; `magicConfirm` consumes the token only on a button press (A13). Android
    back moves to the previous view in the machine.
U2. **Conditional rendering by auth state** at the root: `AuthGate` when signed out, the main app when signed in,
    and a neutral splash while the stored session is being read, so there is no flash of the wrong screen.
    Navigation inside the signed-in app uses the native stack and tabs; that is the mobile form of "single page".
U3. **Zero reload.** No action may require the user to pull, restart or reload to see its result. Mutations update
    the cache (optimistically where specified) and invalidate related queries. The app refetches on foreground.
    Where state must survive a restart (upcoming shifts, theme, last signed-in email), it is persisted.
U4. **State management**: TanStack Query for server data, Zustand for client-only state, secure-store for tokens,
    a query-cache persister for offline shifts. `STATE.md` explains why Zustand was chosen, maps every important piece of data to where it lives
    and why, and explains each cache time.
U5. **Design tokens, no magic numbers.** Colours, type scale, spacing (multiples of 4 or 8), radii, shadows and
    motion durations are tokens defined once. Components use only tokens. A script lists hard-coded colour values
    and stray pixel numbers in component files; the gate requires zero. The values come from the owner's design
    system (U11), never from the agent's taste.
U6. **A proper, beautiful UI**: consistent type scale and spacing rhythm; a designed dark mode (not inverted
    colours) ONLY if the owner's design system provides dark values (U11, Q9); skeleton screens instead of spinners for lists; designed empty, error and end-of-list states;
    Reanimated motion for transitions and key confirmations [VERIFY]; haptics on key actions; tasteful, never
    decorative-for-its-own-sake. The design direction is the owner's design system (U11); the ADR records how it is
    applied, and the owner approves it BEFORE any screen is built.
U7. **Auto focus.** On each auth view the first input receives focus; on views with no input the heading
    receives accessibility focus. After a failed submit, focus the first invalid field. After a successful view
    change, move accessibility focus to the new view's heading. Never trap focus.
U8. **All user-facing strings live in one catalog** (`app/src/i18n/en.ts` plus server error codes mapped to
    catalog keys). No hard-coded user text in components. The auth messages in PRD section 11 are fixed.
U9. **Responsive on every phone.** No fixed widths. Safe-area insets respected. Keyboard never covers the active
    field. Content that does not fit scrolls. No horizontal scrolling. Layout survives text at 200 percent. Verified
    on the size matrix in PRD 6.3 with screenshots saved to `docs/ui-matrix/`.
U10. **Every list and fetch has loading, empty, error and (for lists) end-of-list states.** A blank screen is a bug.
U11. **The owner's design system is the source of values** [DECISION, owner, 18 Oct 2026]. It lives in
     `design-system/` (Material-3 style roles, Poppins, light colour set, spacing, shadows): `convertTokens.js`, the
     three `design-tokens.*.json` files, `design-tokens.material3.json` (the additions below), `verifyTokens.js` and
     the generated `design-variables.css`. (a) NEVER change, add, remove, re-map or "fix" a colour token or colour
     output, and never edit `convertTokens.js`, `verifyTokens.js` or any JSON file; the owner's standing order is "do
     nothing for colors". The owner completed the system on 18 Oct 2026 from Google Material 3 (file
     `design-tokens.material3.json`, each token labelled with its source): the four tokens the old CSS lacked (inverse
     surface, inverse on surface, surface tint, surface tint color), `warning` and `success` (each with `on-`,
     `-container`, `on-…-container` roles and a ramp), the remaining M3 roles (background, scrim, shadow, surface dim
     and bright, inverse primary, fixed roles), `--shape-corner-*` and `--state-*` opacities. Use `--color-error*` for
     errors, `--color-warning*` for warnings, `--color-success*` for success; there is no "info" colour (use primary
     or secondary roles). Run `node design-system/verifyTokens.js` as a gate: it must print 0 errors. (b) The web surface imports `design-variables.css` as it is.
     (c) The app cannot read CSS variables: `app/src/theme/tokens.ts` is generated READ-ONLY from
     `design-variables.css` by `scripts/build-app-tokens.mjs`, which copies values and changes none [DECISION, owner
     confirmed 18 Oct 2026]. The folder is named `design-system` (no space); it was renamed from `Design System` with
     the contents byte-identical (a `blake2b512` digest of each file before and after, recorded in `docs/decisions/`, A4). (d) Do not invent dark colours; dark mode waits for the owner (Q9). (e) Contrast problems are REPORTED in
     `docs/a11y/contrast.md` with the numbers, never repaired in the tokens (X5). (f) Pixel values stay as the
     design system gives them; the app converts the CSS `px`/`rem` text to numbers. (g) Poppins must be loaded
     before first paint [VERIFY the Expo font package and the licence]; a missing font falls back to the system font.
