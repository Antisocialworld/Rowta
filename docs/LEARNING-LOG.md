# Learning log

The agent writes a DRAFT entry per phase (what it does, why this way, what breaks it). The owner rewrites each entry in their own words. The 8 interview answers from the brief go at the end.

## Draft: Phase 0, part A — two databases and Prisma

*Draft for the owner to rewrite.*

**What it does.** Rowta keeps its data in two PostgreSQL databases that run as local containers: one holds the global
data (users, currencies, prices) and is also the first shard, the other is the second shard that holds only team data.
The SQL files in `server/prisma/sql/` are the definition of the tables — they are the single source of truth. This
round ran that SQL against both live databases, ran the built-in checks twice (once as the setup role, once as the
role the app will use), and then taught Prisma — the database toolkit — to talk to both databases without ever being
allowed to change the tables.

**Why this way.** Keeping the table definitions in plain SQL files means nobody's tooling can quietly rewrite the
schema: what the database runs is what is in the repo, and re-running the setup is safe because it skips what already
exists. Money is stored as whole minor units (kobo, cents) in a `bigint` column, so a price can never be a fraction of
a cent or drift through floating point. The app's database role can add rows but cannot edit or delete ledger rows —
the database itself refuses — which is what "the ledger is append-only" means in practice, rather than a promise in
the code.

**What breaks it.** Prisma's "read the live database and describe it" step makes one mistake with our schema: three
relationships that are really "one team has many members" look like "one team has one member" to it, because of a
half-unique index we use to allow only one owner per team. A small script fixes those three lines after every read,
and fails loudly if it ever finds a different number, so a future update to Prisma cannot slip past us. Also, the two
full-text search columns are invisible to Prisma, so search will be written as raw SQL; and Prisma's current
"latest" version is an unfinished test version, so the version is pinned and must be bumped on purpose.

## Draft: Phase 1 — design system, app shell, component kit, auth shell

*Draft for the owner to rewrite.*

**What it does.** The phone app now exists. The owner's design-system colours, type sizes and spacing were turned
into a generated code file (391 values, regenerated by a script, never hand-edited), so nothing in the app can invent
a colour or a size — a lint gate fails the build if someone tries. On top of that sits a small component kit
(buttons, fields, cards, chips, badges, toasts, sheets, dialogs…) that already does the hard accessibility work once:
every button that waits for valid input is dimmed but still focusable and announces why it is waiting; every field
has a permanent visible label; icons that are decoration are hidden from the screen reader. Sign-in and the nine
other auth screens are one screen with ten states, driven by a small tested state machine, so going "back" is
predictable and the Android back button behaves. A gallery screen shows every component in every state for review.

**Why this way.** Auth is views, not pages, because the user should never watch the app reload between "forgot
password" and "enter the code" — the focus moves, a spoken message explains what happened, and the keyboard stays
where it belongs. The state machine is written as a pure function separate from React so it can be tested by simply
typing on a keyboard, no emulator needed; the test proves all ten screens exist, that "back" works, and that at the
first screen "back" lets Android exit instead of looping. The design tokens are generated from the owner's file and
checked for equality, so if the design system changes, one script updates the app and a test proves no colour drifted.

**What breaks it.** There is no real sign-in yet: the "session" is a stub that deliberately refuses to load in a
release build (it throws), and the app refuses to boot with it — a guard, not a comment, recorded in the security
document, to be replaced in Phase 2 by the server's session. The screenshots of every phone size (the "size matrix")
do not exist because this machine has no emulator; the capture script prints exactly what is missing instead of
faking it. Two screen-reader rules are only enforced by static linting, not by a real TalkBack run yet. And one
colour pair in the design system (the tertiary chip) is far too low-contrast for text — it is reported honestly in
the contrast document, not silently "fixed", because changing colours is the owner's call.
