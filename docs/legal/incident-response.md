# Internal: security incident and breach note

Who decides, who is told, and how — written before anything happens. Keep this file factual; store dates and
times in the log at the bottom. Never paste secrets or full personal data into it.

## Who does what

1. **Finder (anyone):** report immediately to the operator by email — [OWNER: add a second contact, e.g. a
   technical adviser] — with what happened, when, and where. Do not try to be a hero; do not delete evidence.
2. **Operator (the owner):** decides if it is an incident, contains it (rotate the affected secret at the
   provider FIRST, then remove it from history — per docs/SECURITY.md), assesses what data could be involved,
   and keeps this log.
3. **Users who are affected:** told by email from rowtareply@gmail.com, in plain language: what happened, what
   data was involved, what we did, what they should do. No jargon, no downplaying.
4. **Regulator:** if the incident is reportable under Nigerian law, notify the Nigeria Data Protection
   Commission. Commentary about the Nigeria Data Protection Act 2023 reports a **72-hour** expectation
   (reported as section 40(2) in a law-firm article). This is **NOT VERIFIED against the NDPC text** — the
   owner must confirm the current rule and deadlines on the NDPC website (see OWNER-INPUTS.md to-do 1).
5. **Lawyer / adviser:** [OWNER: add contact] — consulted before any public statement about a reportable
   breach.

## The steps

1. Contain: stop the bleeding (rotate secret, revoke token, close the door) — provider first, repo second.
2. Record: timeline, affected data, number of people — in the log below, minimal detail.
3. Decide: reportable? (Nigeria first market; other regions if users live there — "verify current text").
4. Tell: affected users by email; regulator within the confirmed deadline once the owner has verified it.
5. Learn: what allowed it, what changes prevent it; update this note if the process changed.
